# CloudKit Private DB for user data, Cloudflare R2 + VPS FastAPI for shared data

User-private data (Watchlist, read state, notification preferences) is stored in CloudKit Private DB as the source of truth, synced across the user's devices via CloudKit. Shared, deduplicated data (filing summaries, event cards, ticker metadata) is stored in Cloudflare R2 as JSON objects, served to the app via a GET endpoint on the VPS FastAPI server (same process that runs the cron worker and `/watchlist` + `/devices` endpoints). On the app side, these two data classes are kept in separate SwiftData containers (see ADR-0006).

Rejected alternatives: CloudKit Public DB for shared data (requires hand-rolled ES256 JWT server-to-server signing in Python, and hits Public DB record limits faster); a single self-hosted backend with its own database (duplicates CloudKit's sync/offline/multi-device story and adds an auth system the MVP doesn't need); a separate Cloudflare Worker (TypeScript) as the read endpoint — this was the original design, but dropped to keep the server side in a single language (Python). The TS EDGAR ecosystem (`sec-edgar-toolkit` v0.1.1, AGPL-3.0) is immature, virally licensed, and lacks the section extraction (Risk Factors, MD&A) that `edgartools` (Python, MIT, v5.39, 2.4k stars) provides natively — making Python the clear choice for the ingestion worker. Splitting the read endpoint into a second language/service to save a few boto3 lines on the VPS is not worth the maintenance cost of a second toolchain. The Cloudflare Worker read endpoint may be reintroduced in v2 if edge latency or read-load offloading becomes relevant.

The trade-off is a split data-access layer in the app (CKContainer for private, HTTP for shared), which is accepted because the two data classes have different semantics anyway.
